# RocksDB C API Gaps

Supplement to [explanation.md](explanation.md), which explains
[why the C API is the whole contract](explanation.md#the-c-api-is-the-whole-contract). For what is
implemented today see [reference.md#feature-status](reference.md#feature-status).

rocksdbffm wraps `rocksdb/c.h` — the official RocksDB C API — not C++ directly. This has two consequences:

- **Type A gaps**: the C API exposes the feature but rocksdbffm has no Java wrapper yet. Actionable now.
- **Type B gaps**: the C API does not expose the feature at all. Requires an upstream PR to `facebook/rocksdb` (`include/rocksdb/c.h` + `db/c.cc` + `db/c_test.c`) before a Java wrapper is possible. Every entry below only touches types that already have a C-API analogue (`Slice`, `Env`, `Logger`, flat parallel arrays as used by `rocksdb_multi_get()`), so a shim is mechanical, not architecturally blocked.

---

## Type A — C API exists, Java wrapper missing

| Feature | Key C functions | Priority | Notes |
|:---|:---|:---:|:---|
| Legacy MultiGet | `rocksdb_multi_get()`, `_cf`, `_with_ts` | Low | Superseded by `rocksdb_batched_multi_get_cf`, which `ReadBatch` wraps — upstream's own comment says these legacy functions get no batching performance benefit, so there's no reason to also wrap them |
| Pinned batched MultiGet | `rocksdb_batched_multi_get_pinned_cf()`, `rocksdb_pinnable_multi_get_count()`/`_result()`/`_destroy()` (new in v11.12) | High | One native owner for every pinned value and error of a batched single-CF MultiGet, read back per index as borrowed `char*`/`size_t` — the zero-copy counterpart of `rocksdb_batched_multi_get_cf`, which `ReadBatch` wraps today with one `rocksdb_pinnableslice_t*` per key. Candidate to back `ReadBatch` directly; benchmark against the current path first. Keys go in as a `rocksdb_slice_t` array rather than parallel pointer/size arrays |
| Get/MultiGet with metadata | `rocksdb_get_with_metadata()`/`_cf_with_metadata()`, `rocksdb_multi_get_with_metadata()`/`_cf_with_metadata()` (new in v11.12) | Low | Plain get/multi-get that also returns the user-defined timestamp of the value found and a `newer_version_present` flag. Only meaningful with user-defined timestamps, which aren't wrapped either (`rocksdb_comparator_with_ts_create()`, see Custom Comparator below) |
| TransactionDB/Transaction MultiGet | `rocksdb_transactiondb_multi_get()`, `rocksdb_transaction_multi_get()`, `_for_update` | Medium | Separate native symbols from the plain `rocksdb_t*` batched call `ReadBatch` already wraps (same story as direct put/get elsewhere on these two types) |
| CompactFiles | `rocksdb_compact_files()`, `rocksdb_compaction_options_t` + setters (incl. `output_temperature_override`) | Low | A second, unrelated options opaque type from `CompactOptions`'s `rocksdb_compactoptions_t` (used by `compactRange`) — needs its own wrapper class, not an extension of `CompactOptions.java` |
| WriteBatchWithIndex | `rocksdb_writebatch_wi_*` (39: create/put/delete/merge/put_log_data, save points, `create_iterator_with_base(_cf)`, `get_from_batch(_cf)`, `get_from_batch_and_db(_cf)`, `get_pinned_from_batch_and_db(_cf)`) | High | Queryable write batch — point lookups and an iterator that overlay the batch's pending writes on the DB/snapshot before it's committed ("read your own writes" without a full `Transaction`). No callback plumbing; same `NativeObject` shape as `WriteBatch.java`, which already covers the plain put/delete/merge/deleteRange surface this would extend |
| Table Properties | `rocksdb_table_properties_*` (~60 accessors: compression/filter/index sizes, comparator/merge-operator/filter-policy names, block counts, creation/file timestamps, user-collected properties; `_oldest_ancestor_time` and `_lsm_info_at_creation` new in v11.12) | Medium | SST-level metadata introspection; self-contained, no callback plumbing needed — likely surfaced via `getLiveFiles()`/`getLiveFilesStorageInfo()`'s existing per-file views or a new `TableProperties` lazy view following the same shape |
| CF/SST structure introspection | `rocksdb_get_column_family_metadata()`/`_cf`/`_with_options`, `rocksdb_column_family_metadata_*` (6), `rocksdb_column_family_metadata_options_*` (7), `rocksdb_level_metadata_*` (5), `rocksdb_sst_file_metadata_*` (5) | Medium | Per-level/per-file breakdown of a CF (`GetColumnFamilyMetaData`) — distinct from `LiveFiles`/`LiveFilesStorageInfo` (which enumerate files needed to reconstruct the DB, not the level structure); same lazy-per-field-view shape as those two |
| WriteBufferManager flush policy | `rocksdb_write_buffer_manager_create_with_policy()`, `_create_with_cache_and_policy()`, `_flush_policy()`/`_set_flush_policy()` (`oldest`/`largest`/`largest_across_dbs`, new in v11.12) | Low | Which memtable to flush once the budget is hit; the rest of `WriteBufferManager` is wrapped. An int enum, so it needs its own `fromValue` enum, plus two more factory overloads |
| Memory accounting | `rocksdb_approximate_memory_usage_create()`/`_destroy` + 4 `_get_*` accessors, `rocksdb_memory_consumers_create()`/`_add_cache`/`_add_db`/`_destroy` | Low | `GetApproximateMemoryUsageByType` equivalent; ops/monitoring value, no callback plumbing |
| Export/Import CF metadata | `rocksdb_export_import_files_metadata_create()`/`_destroy`, `_get_db_comparator_name`/`_set_db_comparator_name`, `_get_files`/`_set_files` (pairs with `ExportColumnFamily`/`CreateColumnFamilyWithImport`, not yet checked for separate C entry points) | Low | Supports CF export/import (e.g. cluster resharding); untracked, needs the paired export/import entry points confirmed before scoping |
| DB-level checksum verification | `rocksdb_verify_checksum()`/`_with_options`, `rocksdb_verify_file_checksums()`/`_with_options` | Medium | Whole-DB integrity check, distinct from `BackupEngine`'s verify; small and cheap to add |
| Load/parse options | `rocksdb_load_latest_options()`/`_destroy` (reopen a DB with the exact `OPTIONS-*` file it was created with, instead of hardcoding options in Java), `rocksdb_get_options_from_string()` (parse option overrides from a string onto a base `Options`) | Medium | 3 functions; reuses `Env`/`Cache`/`Options` wrappers already in place, no new domain type needed |
| Multi-path storage (`DbPath`) | `rocksdb_dbpath_create()`/`_destroy`, `rocksdb_options_set_db_paths()` | Low | Per-path target size for tiered storage across multiple mount points; small, self-contained |
| Range file deletion | `rocksdb_delete_file_in_range()`/`_cf` | Low | Deletes whole SST files that fall entirely within a range, distinct from `compactRange`'s rewrite-based approach |
| Custom Comparator | `rocksdb_comparator_create()`, `rocksdb_comparator_with_ts_create()` | High | Custom key ordering; note: key shortening not exposed in C API |
| WAL Filter | `rocksdb_walfilter_create()` (`state`/`destructor`/`name` + two callbacks: `rocksdb_walfilter_column_family_log_number_map_cb`, `rocksdb_walfilter_log_record_found_cb`), `rocksdb_options_set_wal_filter()`/`_clear_wal_filter()` | Medium | **Miscatalogued as Type B until 2026-09-04** — the full callback-based type exists in `c.h`. Same `state_`/`destructor_`/`name_` shape as `CompactionFilter`/`MergeOperator.Custom`, but `log_record_found`'s callback is more involved: it receives a `rocksdb_writebatch_t*` and can hand back a replacement `rocksdb_writebatch_t*` plus a changed-flag, and `column_family_log_number_map` takes several parallel `uint32_t*`/`uint64_t*`/`char**` arrays (same pattern already handled for `rocksdb_multi_get`). Selective WAL replay at recovery time |
| JemallocNodumpAllocator | `rocksdb_jemalloc_nodump_allocator_create()` | Medium | Jemalloc allocator for caches; avoids coredump leaking sensitive data |
| Advanced column family options | `rocksdb_options_set_target_file_size_multiplier`, `_set_max_bytes_for_level_multiplier`, `_set_min_write_buffer_number_to_merge`, `_set_level_compaction_dynamic_level_bytes`, `_set_compression_per_level`, `_set_periodic_compaction_phase_recovery_percent` and `_set_blob_file_writable_file_max_buffer_size` (both new in v11.12), etc. | Low | Remainder after `write_buffer_size`/`num_levels`/`level0_file_num_compaction_trigger`/`target_file_size_base`/`max_bytes_for_level_base`/`max_write_buffer_number` were mapped (see `Options.java`'s "LSM shape and compaction triggers" section) — multiplier/secondary knobs layered on top of those base values |
| Key common-prefix optimization | `rocksdb_block_based_options_set_optimize_key_common_prefix()`/`_get_` (new in v11.12) | Low | Smaller index/data blocks plus a faster `Seek` for bytewise comparators; an int enum (`kDisabled`/`kIfFastSeek` (default)/`kEnabled`). Only takes effect at `format_version` >= 8 with delta encoding on, so the default already does the right thing for most callers — wrap alongside the other `BlockBasedTableOptions` enums |
| Merge throttling | `rocksdb_options_set_max_successive_merges`/`_get_`, `_set_strict_max_successive_merges`/`_get_` | Low | Caps how many merge operands `Get()`/compaction will chain before forcing a resolve; independent of which `MergeOperator` is configured |
| Scan-triggered flush | `rocksdb_options_set_memtable_op_scan_flush_trigger`/`_get_`, `_set_memtable_avg_op_scan_flush_trigger`/`_get_` | Low | Newer heuristic: forces a memtable flush once a range scan touches this many (or this running-average many) entries per operation — a different concern from the memtable bloom/arena tuning already mapped (see `Options.java`'s "Memtable tuning" section), aimed at range-scan-heavy workloads rather than the hash/prefix lookup path |
| `rocksdb.live_sst_files_size_at_temperature` property | `rocksdb_property_value()` (existing, generic) | Low | `Temperature` already exists; what's missing is a suffixed-property call shape (`name:kWarm`) `getProperty(Property)`'s flat enum doesn't support — every other property is a plain constant, this one alone takes a parameter |

## Type B — No C API yet (upstream contribution needed)

Each entry requires adding an opaque type, factory function(s), and option setters to `rocksdb/c.h` and implementing them in `db/c.cc`.

| Feature | C++ header | What c.h needs | Notes |
|:---|:---|:---|:---|
| SecondaryCache | `rocksdb/cache.h` | `rocksdb_secondary_cache_t`, `rocksdb_compressed_secondary_cache_create()`, `rocksdb_lru_cache_options_set_secondary_cache()` | Compressed in-memory L2 tier; discussed in [secondary-cache PR discussion](https://github.com/facebook/rocksdb/issues) |
| Capped-prefix SliceTransform | `rocksdb/slice_transform.h` | `rocksdb_slicetransform_create_capped_prefix(size_t)` | **Upstream PR filed:** [facebook/rocksdb#15141](https://github.com/facebook/rocksdb/pull/15141). Only `NewFixedPrefixTransform` is exposed via `rocksdb_slicetransform_create_fixed_prefix()` ([SliceTransform.java](../core/src/main/java/io/github/dfa1/rocksdbffm/SliceTransform.java)); `NewCappedPrefixTransform` — same idea but `InDomain()` always returns `true`, truncating rather than excluding keys shorter than the cap — has no C API entry point yet. Unlike most Type B entries here, rocksjni does *not* share this gap — `Options#useCappedPrefixExtractor`/`ColumnFamilyOptions#useCappedPrefixExtractor` (`java/rocksjni/options.cc:1191`/`:4386`) call `NewCappedPrefixTransform` directly against the C++ API via JNI, something only possible because JNI isn't restricted to `c.h` the way this project's C-API-only FFM approach is |
| TieredCache | `rocksdb/cache.h` | `rocksdb_cache_create_tiered()` + `rocksdb_tiered_cache_options_t` | Combines primary LRU with compressed secondary; single cache_t result |
| Shared/external Statistics object | `rocksdb/statistics.h` | A standalone `rocksdb_statistics_t` create/destroy pair plus an `rocksdb_options_set_statistics()` setter | `c.h` only exposes statistics inline per-`Options` (`rocksdb_options_enable_statistics()` + the `rocksdb_options_statistics_get_string`/`_get_ticker_count`/`_get_histogram_data` query accessors, already reachable from `Options.enableStatistics()`); there is no way to build one `Statistics` object and attach it to several `Options`/DBs the way C++'s `std::shared_ptr<Statistics>` does. Confirmed gap during a production `rocksdbjni` migration whose `BlockCacheBuilder` shared one `Statistics` instance across multiple DB instances — dropped, with no rocksdbffm equivalent. See [how-to.md](how-to.md#inspect-properties-and-statistics) for the Java-side ticker-summing workaround in the meantime |
| SST File Reader | `rocksdb/sst_file_reader.h` | `rocksdb_sst_file_reader_t`, open, new_iterator, get_table_properties, verify_checksum, destroy | Offline SST inspection; not exposed in c.h at all |
| Custom SstPartitioner | `rocksdb/sst_partitioner.h` | `rocksdb_sst_partitioner_t` (state/destructor/name/`should_partition`/`can_do_trivial_move` fn pointers) + a callback-based `rocksdb_sst_partitioner_factory_create()` | Only the built-in `rocksdb_sst_partitioner_fixed_prefix_factory_create()` is exposed today ([SstPartitionerFactory.java](../core/src/main/java/io/github/dfa1/rocksdbffm/SstPartitionerFactory.java)); a caller-supplied `ShouldPartition`/`CanDoTrivialMove` implementation has no C API entry point, unlike `CompactionFilterFactory`. The shim would mirror `rocksdb_compactionfilterfactory_t` (`db/c.cc`) — same `state_`/`destructor_`/`name_` shape, different callback signatures — so it's mechanical, not architecturally blocked. rocksjni has the identical gap: `org.rocksdb.SstPartitionerFactory` is an abstract `RocksObject` with no overridable methods |
| Custom Env (fault injection) | `rocksdb/env.h` | `rocksdb_env_create()` (state/destructor + fn pointers for the `Env`/`FileSystem` virtual surface: `NewSequentialFile`/`NewRandomAccessFile`/`NewWritableFile`/`DeleteFile`/`FileExists`/etc.) | `rocksdb_env_t` (`db/c.cc`) is just `{ Env* rep; bool is_default; }` — a fixed pointer to a pre-built C++ `Env`, not a `state_`/`destructor_`/callback shape like `rocksdb_compactionfilter_t`/`rocksdb_slicetransform_t`/`rocksdb_logger_t`. `c.h` only offers `rocksdb_create_default_env()` and `rocksdb_create_mem_env()`; there is no way to author a custom `Env` (e.g. one that injects I/O failures for unit tests, mirroring RocksDB's own C++-only `FaultInjectionTestEnv`) from the C API today. Substantially larger than most Type B entries: `Env` has dozens of virtual methods, vs. 1-2 callbacks for `CompactionFilter`/`SliceTransform`; an upstream shim would likely need to start with a narrow file-I/O subset rather than the full interface |
| Persistent Cache | `rocksdb/persistent_cache.h` | `rocksdb_persistent_cache_t`, `rocksdb_persistent_cache_create(env, path, size, log, optimized_for_nvm)` | `NewPersistentCache()` only takes `Env*`/`Logger` (both already have `rocksdb_env_t`/`rocksdb_logger_t` shims) plus scalars — same shape as `rocksdb_rate_limiter_create()` |
| Wide Columns | `rocksdb/wide_columns.h` | `rocksdb_put_entity()`, `rocksdb_get_entity()`, `rocksdb_pinnablewidecolumns_t` | `WideColumn` is a name/value `Slice` pair; `WideColumns` is a vector of those — expressible as parallel `char**`/`size_t*` arrays exactly like `rocksdb_multi_get()` already does |
| Library version query | `rocksdb/version.h` | A `rocksdb_version()`-style function returning `ROCKSDB_MAJOR`/`ROCKSDB_MINOR`/`ROCKSDB_PATCH` | These are C++ preprocessor macros, not runtime-queryable through `c.h`. The official JNI binding gets this via a custom native method in its own `rocksjni.cc` that reads the macros directly — not available to a C-API-only wrapper. We currently only know the version via the pinned submodule tag (see `AGENTS.md`); no way to ask the loaded native library at runtime |
| Custom `UserDefinedIndexFactory` (UDI) | `rocksdb/user_defined_index.h` | A callback-based `rocksdb_udi_factory_create()` (state/destructor + `NewBuilder`/`NewReader` fn pointers), mirroring `rocksdb_compactionfilterfactory_t`'s shape | `UserDefinedIndexFactory` extends `Customizable`, so the three C API entry points that do exist (`rocksdb_block_based_options_set_user_defined_index_factory_from_string`/`_clear_`/`_get_..._name`) only let a caller *activate a factory already registered in C++* by name — they call `Customizable::CreateFromString` under the hood, not a constructor taking function pointers. That string-based trio is already wrapped (`BlockBasedTableOptions.setUserDefinedIndexFactoryFromString` and friends, see [reference.md](reference.md#table-options-caches-filters)) and lets a caller opt into RocksDB's one built-in implementation, `TrieIndexFactory` (`rocksdb/utilities/trie_index/`), if it's linked into and self-registered in the built `librocksdb`. But the feature's actual headline capability — defining your own index format in Java, the way `MergeOperator.custom()` lets you write `fullMerge` in Java — has no C API hook at all; `UserDefinedIndexFactory::NewBuilder()`/`NewReader()` are pure C++ virtual methods with no shim |
| Remaining `EventListener` callbacks | `rocksdb/listener.h` | More callback params on `rocksdb_eventlistener_create()` (or a `_v2`), plus opaque info types (`rocksdb_fileoperationinfo_t`, `rocksdb_tablefilecreationinfo_t`, ...) | `c.h` exposes 10 of the 32 C++ callbacks, all wrapped in [EventNotifier](../core/src/main/java/io/github/dfa1/rocksdbffm/EventNotifier.java) except the two subcompaction ones. Missing 22: file I/O (`OnFileReadFinish`/`WriteFinish`/`FlushFinish`/`SyncFinish`/`RangeSyncFinish`/`TruncateFinish`/`CloseFinish`, gated by `ShouldBeNotifiedOnFileIO()`), `OnIOError`, error recovery (`OnErrorRecoveryBegin`/`End`/`Completed`), SST/blob lifecycle (`OnTableFileCreationStarted`/`Created`/`Deleted`, `OnBlobFileCreationStarted`/`Created`/`Deleted`), `OnBackgroundJobPressureChanged`, `OnCompactionPreCommit`, `OnManualFlushScheduled`, `OnDBShutdownBegin`, `OnColumnFamilyHandleDeletionStarted`. File I/O is the most valuable for [#200](https://github.com/dfa1/rocksdb-ffm/issues/200): JFR's `jdk.FileRead`/`jdk.FileWrite` only see Java I/O, never RocksDB's native reads |

## Contributing

For **Type A**: add a Java wrapper class following the `NativeObject` pattern, wire FFM upcall stubs for callback-based APIs.

For **Type B**: open a PR to `facebook/rocksdb` adding the C shim, then add the Java wrapper. The secondary cache PR is a good starting point and was discussed in the project issue tracker.
